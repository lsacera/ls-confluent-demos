  • WARNING: 15% deviation from normal range (predictive maintenance opportunity)
  • CRITICAL: 25% deviation from normal range (immediate action required)
- Automatic alerting with full context (location, value, threshold, timestamp)

HEALTH STATUS:

it goes completely offline.

This is predictive maintenance in action: fix sensors based on actual health
data, not arbitrary 6-month schedules."

--- ARCHITECTURE PAGE ---
"Let's look under the hood at the streaming architecture."

DATA PIPELINE:
-------------
1. SCADA Simulator (representing real sensors)
   ↓
2. Kafka Topics (scada-telemetry, scada-alerts)
   ↓
3. Apache Flink Processing (5 real-time queries)
   ↓
4. PostgreSQL (materialized views)
   ↓
5. Web Dashboard (real-time visualization)

FLINK STATEMENTS:
"These are the 5 Flink SQL queries running continuously:

1. Telemetry Stream: Structured stream with watermarks for out-of-order event handling
2. Anomaly Detection: Real-time threshold monitoring with 2-tier severity (15%/25%)
3. Zone Aggregations: 5-minute tumbling windows for zone-level power and voltage stats
4. Grid Region Stats: 10-minute windows calculating stability scores and power balance
5. Sensor Health: 1-minute windows tracking reading frequency (expects 12/min per sensor)

Each query processes 2,160 events per minute (180 sensors × 12), performing:
- Windowed aggregations across time and geography
- Complex calculations (grid stability formula, consecutive failure tracking)
- Materialized view updates to PostgreSQL via sink connector
- All with <1 second end-to-end latency

The beauty of Flink SQL is operators don't need Java/Scala developers. These
are declarative SQL queries that business analysts can understand and modify."

KAFKA TOPICS:
"Topic metrics show:
- Messages per second (throughput)
- Total message count (volume over time)
- Partitions (parallel processing capability)

This visibility helps operations monitor the health of the streaming
platform itself."

SECTION 5: TECHNICAL ARCHITECTURE DEEP DIVE (2 minutes - if time permits)
================================================================================

"Let me briefly explain the technical foundation:

CONFLUENT CLOUD COMPONENTS:
--------------------------
• Kafka Cluster: Handles 2,000+ messages/minute with millisecond latency
• Apache Flink Pool: Runs 5 continuous SQL queries processing streams
• Schema Registry: Ensures data quality with Avro schemas
• Connectors: PostgreSQL sink for materialized views

KEY TECHNICAL CAPABILITIES:
--------------------------
1. Exactly-Once Semantics: No duplicate alerts or missed events
2. Watermarking: Handles out-of-order events from sensor network
3. Windowed Aggregations: Time-based processing (1-min, 5-min, 10-min windows)
4. Stateful Processing: Tracks consecutive failures, running averages
5. Scalability: Auto-scales from 180 to 18,000 sensors without code changes

WHY CONFLUENT vs TRADITIONAL SCADA:
-----------------------------------
Traditional:
  - Polling-based: Check sensors every 5-15 minutes
  - Batch processing: Analyze data in scheduled jobs
  - Siloed: Separate systems for different functions
  - Limited scalability: Hardware constraints

Confluent Approach:
  - Event-driven: Process as data arrives
  - Real-time: Millisecond latency end-to-end
  - Unified platform: One system for all streaming needs
  - Cloud-native: Infinite scalability, zero infrastructure management

The result? Faster detection, better decisions, lower operational costs."

COMMON QUESTIONS & ANSWERS:
--------------------------

Q: "How does this integrate with our existing SCADA system?"
A: "Confluent acts as a real-time data layer. Your existing SCADA can continue
    to operate while we add streaming capabilities. We've integrated with
    Siemens, ABB, GE, and other major SCADA vendors. Common patterns:
    - OPC UA connectors pull data into Kafka
    - Protocol converters for Modbus, DNP3
    - REST APIs for modern systems
    The key is non-disruptive: add capabilities without replacing existing
    infrastructure."

Q: "What about latency and real-time guarantees?"
A: "End-to-end latency is typically <1 second from sensor to dashboard.
    For critical alerts:
    - Sensor reading arrives in Kafka: <100ms
    - Flink processing (watermark, window, aggregation): <200ms
    - PostgreSQL sink: <200ms
    - Dashboard update (10-sec polling): <500ms avg
    Total: Under 1 second detection + up to 10 seconds for display refresh

    For truly critical scenarios (frequency deviation), you'd add Kafka
    consumers for sub-second notifications directly from the alerts topic,
    bypassing the dashboard entirely."

Q: "How does this handle sensor data quality issues?"
A: "Great question. We use Avro schemas to validate every message. Invalid

    - Out-of-range values (sensor miscalibration)
    - Timestamp anomalies (clock drift)
    - Missing fields (protocol issues)
    - Duplicate readings (network retries)
    Data quality monitoring is built into the streaming pipeline."
